## Project

Kinfolk is a family tree maker where relatives each keep their own tree and then link them, so the combined graph shows how several families actually join up. Private repo, GitHub OAuth sign-in.

The distinguishing feature is the combined view: two people who have never met can both record the same grandparent, and Kinfolk merges those records without either side losing their own data.

It is also a contact graph, not only a pedigree. Anyone can be a node -- a friend, a colleague, a neighbour -- and any two nodes can carry a named relation with their own contact details attached.

## The data model, in five sentences

Read this before adding a table or a query -- most "obvious" schema changes here are wrong.

1. **A family tree is a DAG, not a tree.** Two hierarchical edge kinds (partner, parent-child), and the same human can be described by several users independently.
2. **Parentage hangs off a `unions` row, never a (father, mother) column pair.** Remarriages, half-siblings, single parents, and adoption then fall out for free instead of each needing a special case. A child can belong to two unions (birth and adoptive), which is why parentage is not a column on `people`.
3. **`people` is a claim, not a person.** "Your grandfather and my grandfather are the same man" is a consent-gated `person_links` row, never a destructive rewrite -- both owners keep their rows and unlinking restores separate views.
4. **`person_relations` holds every non-hierarchical connection** (cousin, friend, colleague, mentor, neighbour...) as one row per pair per kind. It is a separate table from `unions` because a friendship carries no generation, so it must never reach the layout engine.
5. **`contact_details` is rows, not columns.** One row per channel per person, each carrying its own visibility. A phone column could not hold two numbers and would need a migration every time a new platform appeared.

## Gotchas

- **An edit writes to a SOURCE row, never to `FusedPerson.id`.** The fused id is the smallest member id (a uuid comparison, chosen in `fuseTrees` so output never depends on input order), so on a person described by two families it is the FAR family's row about half the time -- and `treeIdForEditablePerson` would refuse the write, telling somebody they may not edit their own record. `editTarget()` in [lib/tree/editable.ts](lib/tree/editable.ts) resolves the contributing row that sits in a tree the viewer may write to. Verified against the exact trap: a merged person with fused id `aaa` (theirs) resolves to `zzz` (mine). It takes a LIST of editable trees rather than the view's single `editableTreeId`, because a viewer can hold grants on several graphs and a merged person can carry a row in more than one.
- **A form must be prefilled from the TARGET row, not from `primary`.** `primary` is whichever contributing row won the display contest (the viewer's own tree if present, else most recently updated), so on a merged person it can hold the far family's values -- and a form prefilled from their row copies their data into yours the moment you press save. A corruption with no visible tell, which is why `editInitialValues()` exists rather than reading `person.primary` at the call site.
- **`updatePerson` patched by KEY PRESENCE, and the version that did not was silently destructive.** It wrote every column unconditionally, and `orNull(form.get("x"))` is null for a field the form never rendered -- so saving a compact edit NULLED `birthFamilyName`, `deathPlace` and `sourceNote`. A birth surname is searchable ([lib/tree/search.ts](lib/tree/search.ts)), so that was data loss on a field the user could not even see. The rule now: an ABSENT key is left alone, a key present but BLANK is a deliberate erasure. That is the only rule under which a partial form is safe, and it lets one action serve a compact quick-edit and a full form. The decision lives in [lib/tree/person-patch.ts](lib/tree/person-patch.ts) so it is pure and asserted (12 unit tests plus live checks proving birth surname, source note and occupation survive a four-field edit).
- **`verification` is not user-editable, and its absence from the edit form is the point.** It is a provenance claim the card renders as a tick, so letting somebody mark their own row `documented` would turn the strongest evidence level into a self-assessment -- which is exactly what the separate `self_confirmed` level already means without overstating it. `treeId`, `claimedByUserId` and the `verified*` columns are omitted for the same reason: a tree id would move a person between graphs.
- **A `"use server"` export is not callable from a plain script**, so `typeof updatePerson` in a smoke check read `"undefined"` and asserted nothing. Importing one yields a server-reference stub. Test the pure rule the action delegates to instead; the action's own auth path is covered by `smoke-db.mts`.
- **`basePath` rewrites `<Link>`, assets and `redirect()`, but NOT `NextResponse.redirect(new URL(...))`.** That builds an absolute URL from the request origin and Next leaves it verbatim, so under a `/kinfolk` mount `app/demo/route.ts` sent visitors to `/tree` -- which 404s. The shared demo link was broken on the deployed site and fine everywhere else, which is the worst way for it to break. The handler applies `NEXT_PUBLIC_BASE_PATH` by hand; verified end to end (`/kinfolk/demo` -> 307 -> `/kinfolk/tree` 200).
- **On a shared domain a cookie must be scoped by PATH, not just named.** Kinfolk sits at `sagargupta.online/kinfolk` beside other projects on the same host, and cookies are scoped by host and path only -- never by port, never by project. Namespacing the session cookie's NAME stops this app reading a neighbour's; `path: BASE_PATH` stops a neighbour reading a live session token of ours. The session cookie's `secure` was also hardcoded `false`, correct for `http://localhost` and wrong the moment it deploys; it is now derived from `NODE_ENV`.
- **`sagargupta.online/kinfolk` needs the APEX moved off GitHub Pages, and proxying back is impossible.** The domain resolves to Pages (`185.199.108-111.153`) and Pages serves static files only, so it cannot route a subpath to a server. Letting Vercel own the apex and rewrite everything else back to Pages fails too: with a `CNAME` file present, `sagargupta16.github.io` 301-redirects to the custom domain unconditionally (verified, including with a `Host` override), so the proxy would loop forever. Until the apex migrates, deploy with `NEXT_PUBLIC_BASE_PATH` UNSET -- a base path with nothing routing to it serves a page whose every asset 404s.
- **The Neon HTTP driver has NO transactions, so `db.transaction()` throws at runtime while type-checking perfectly.** `lib/db/client.ts` uses `drizzle-orm/neon-http`, whose session throws "No transactions support in neon-http driver" the moment a transaction opens. The first `addRelative` wrapped its five writes in one and would have failed on every single use; `pnpm db:smoke:kin` is what caught it, because nothing offline can. Multi-write actions must therefore be SEQUENCED so a partial failure is harmless, and the order is the design: the union goes first, because a union with an empty partner slot is an ordinary shape this app already renders (a single parent) while a person created with no union is somebody stranded on the canvas with nothing to say why they are there.
- **A quick-add is relationship-first, and `planKin` in [lib/tree/kin-plan.ts](lib/tree/kin-plan.ts) is why it can be.** Recording a father through the raw primitives took four steps and a schema lesson -- create person, create union, add partner, attach child -- and doing it twice for a father and a mother produced TWO single-parent unions, which draws two junctions and no couple. That is the worst class of bug here: it looks like a rendering fault, so nobody suspects the data. The planner finds an existing parent union with a free slot BEFORE creating one, which is the whole fix, and it is pure so the rule is asserted rather than eyeballed (23 unit tests plus 10 live checks in [scripts/smoke-kin.mts](scripts/smoke-kin.mts)).
- **A gender field is drawn ONLY for the three roles that imply nothing, and a posted `sex` can never override one that does.** Six of the nine quick-add roles state a sex ("father" is male), so a picker there would be a field whose only use is to contradict the button just pressed. But `partner`, `child` and `sibling` genuinely imply nothing, and the first version shipped without the field at all -- so those three were permanently `unknown` with no way to record what somebody knew. `addRelative` honours a posted `sex` only when `ROLE_SEX[role] === "unknown"`: the field cannot exist in the form for a gendered role, so a value arriving alongside `role=father` is a forged post rather than a choice. Pinned by tests that assert the override is refused for all six. Deliberately NOT adopted from the research: FamilySearch's rule that sex cannot stay unspecified once somebody is linked as a spouse or parent, and Gramps' gender-filtered parent pickers -- both contradict a schema whose `sex` defaults to `unknown`, and a gender filter here would hide most of the graph from its own picker.
- **Deriving sex from a chosen ROLE is allowed; deriving it from a NAME is not.** The standing rule forbids reading "Maria" and storing `female`, because the user never said anything. Clicking "father" IS a statement about the person being added, so `ROLE_SEX` stores what they said -- and storing `unknown` instead would contradict them. `partner`, `child` and `sibling` stay neutral because those words genuinely imply nothing.
- **A bare birth year goes in `birthDateApprox`, never `birthDate`.** `birthDate` is a real `date`, so "1952" is not a value it can hold, and coercing it to 1952-01-01 invents a birthday nobody recorded -- exactly the false precision the separate `*Approx` columns exist for. `birthYearColumns()` also bounds the year (1000-2200), because "19" and "20255" are typos that would be indistinguishable from a real value once stored.
- **A batch of children gets NUMBERED placeholders, and no shared dates.** `addPerson` rightly refuses a nameless person, and a nameless row renders as "Unknown" indistinguishable from every other, so a batch names them "Son 1", "Son 2" against an offset of what the union already holds -- otherwise a second batch produces two people called "Child 1". A birth year is never applied to a batch: stamping five children with one year asserts they were all born in it.
- **An edge that meets a union must terminate on the dot's CENTRE, which React Flow will not do for you.** It anchors edges to HANDLES and offsets handles outward from the node box, so on a 12x12 junction a partner edge stopped 9px above the dot and the child edge began 9px below: measured 173 and 191 against a centre of 182, an 18px dead zone with the dot floating in it, which is the visibly broken line. The edge cannot fix it from inside, because by then `sourceY`/`targetY` ARE the handle positions -- so `TreeCanvas` passes each junction's centre down as `sourceHub`/`targetHub` and every generator snaps to it. Verified live: 150 of 150 junction endpoints on their dot centre, 0 off.
- **Testing `data` for truthiness is not the same as testing the field a branch needs.** Once every edge carried `data` for the junction anchor, partner edges (which have no sibling bar) fell into the elbow branch and read `bar.barY` as `undefined` -- emitting a path of literal `NaN`s whose `getTotalLength()` is 0, so the couple's line vanished entirely. The guard is `typeof bar.barY === "number"`.
- **ELK places a union dot to minimise crossings, not between the couple, so [lib/tree/layout.ts](lib/tree/layout.ts) slides it afterwards.** Measured on the sample tree: ALL 34 couples had their dot off the midpoint between the partners, the worst by 498px -- and a dot beside a couple rather than between them makes the drop to the children look like it leaves from nowhere. `centreUnionDots()` moves x only (the y ELK assigned is what keeps the dot in its generation gap) and prefers the COUPLE's midpoint over the children's, since the dot's job is to say "these two are partners" while the bracket below already spans the children. A post-layout nudge for the same reason `siblingBars` is: the skeleton must not shift for cosmetics. Now 0 of 34 off.
- **The dot level carries a FIRST name, and the width is measured rather than chosen.** A bare mark showed the shape of the family and nothing else, so finding anybody meant going back to cards and losing the overview. Across all 117 people at 9px mono a first name needs 45px at p90 and 51px at the widest, where a full name needs 84px -- which would make this level nearly as wide as the compact row it exists to be smaller than. Hence a 56x34 slot, and `LEGIBLE_ZOOM.dot` raised 0.18 -> 0.42: at 0.18 a 9px label renders 1.6px tall, which is present in the DOM and unreadable, and that reads as a rendering fault rather than as an overview.
- **A connector's corners live in [lib/tree/paths.ts](lib/tree/paths.ts), because a hand-built path forgets to round them.** The sibling-bar route was assembled from `L` commands only, so 82 of 150 edges turned through hard 90 degree corners while `CORNER_RADIUS` sat unused in the fallback branch -- and one shared bar ran 6013px against a 200px median, a line crossing the whole canvas. Now every turn is a clamped quadratic (clamped to half of each leg, or a child almost directly below its parent bulges sideways past where it started), a family wider than `MAX_BAR_SPAN` is drawn as per-child curves instead of a bracket nobody can take in at once, and the bracket's ends turn DOWN so it closes as one mark rather than reading as a rule. Verified live: hard-corner paths 82 -> 3, and the three remaining are straight vertical drops with no corner to round.
- **The orbit's angles were the defect, not its curves, and three tuning passes on the bow proved it.** Placing each ring by index alone gave a median edge span of 122 degrees with 26 of 34 edges crossing more than 90 -- a parent on ring 1 and its child on ring 2 got independent positions and routinely landed on opposite sides of the circle, so every edge had to cross the middle. Bowing them harder just turned chords into loops. Wedge allocation (each node placed inside its predecessor's angular sector) took the median to 1 degree and 0 over 90. **When a graph looks tangled, measure the angular separation before touching the path generator.**
- **In the orbit, wedges decide ORDER and even spacing decides GAPS, and conflating them makes the radius unbounded.** Sizing a ring on its tightest allocated slot solves `slot * r >= width + gap`, which grows without limit as a slot narrows: one crowded family took the outermost ring to 3641px, then to 9291px with a 17024px edge once unions were collapsed away. Capping the radius instead broke the no-overlap guarantee, because the two cannot both hold. So `ringRadius(count)` sets the radius and nodes are placed at even intervals in wedge order -- families stay contiguous (short edges) while every card gets an equal slot (no overlap). Final: max radius 1680px, longest edge 2817px, and 19/16/21/19 nodes across the four quadrants.
- **The orbit places PEOPLE only; union dots are traversed through, never ringed.** CLAUDE.md already says a union dot is "the MARRIAGE, not a route to the children", and this view takes that literally: counting a junction as a hop put a spouse alone on ring 1 while parents and children shared ring 2, and it spent a full 168px ring step on a 12x12 mark every other generation. `collapseUnionEdges()` rewrites partner and child edges person-to-person (2 + N becomes 1 + 2N, affordable because the orbit shows at most four rings), and `hopsFrom` takes an `isUnion` predicate so a ring means "people I am N relationships from".
- **3D is applied to the CARD, never to the pane, and per-card is also the version that works.** A canvas-wide `perspective` + `rotateX` was the obvious implementation and is wrong: React Flow owns each node wrapper's 2D `translate`, so tilting an ancestor leaves the layout and the picture disagreeing about where a card is, and the SVG brackets (drawn in flat coordinates) no longer meet the cards they join. Per-card was verified empirically rather than reasoned about -- a card under `rotateX(45deg)` measured 132px -> 94px, three hit-probes down its face all landed inside it, and its click still fired, because the browser's own hit-testing follows a CSS transform. Confirmed on the real canvas at 151 tilted nodes: 13 of 14 visible tilted cards clickable, the exception sitting under a toolbar panel.
- **A touch target inside a scaled canvas must also be CAPPED at the size of what it belongs to.** `calc(44px / var(--kf-zoom))` is correct for the floor and unbounded upward: at 0.4 zoom that is 110 layout pixels, which measured wider than the whole 32x17 card, so `elementFromPoint` at a card's centre returned the fold BUTTON and clicking a person opened a fold instead of their panel. A control may overhang its card's edge; it may never eclipse it.
- **The MAJORITY state gets no colour, on every surface that draws it.** 94 of 117 people in the sample tree are living, so a green living-rail put a saturated 7.36:1 stripe on 80% of the cards -- brighter than the NAME above it (rail luminance 0.366 against the card's 0.0065) -- and at fit zoom the tree read as rows of green dashes rather than as a family. The same fact wearing the same colour appeared three times: the card rail, 93 of 152 minimap rects, and 93 of 117 dots in dot mode, where one amber pixel for the viewer had to compete with a green mass. Living is now unpainted (card), `--color-edge` (minimap and dots); deceased keeps the quiet grey because it is the minority (23), and `unknown` keeps its hairline because an unrecorded status is a real stored value. Every individual green cleared its contrast floor -- only the screenshot showed that 94 of them shared a canvas, which is the same lesson as the presence-ring fog reached from the other side.
- **A touch target inside the canvas must be sized in `1 / zoom`, because everything in `.react-flow__viewport` is in a scaled layer.** A `size-11` (44px) fold button measured 35px on screen at 0.785 zoom and would be 7px at the 0.15 floor. The fix is `calc(44px / var(--kf-zoom, 1))` with `--kf-zoom` published onto the viewport element by TreeCanvas, so the hit area is 44 SCREEN px at every zoom (verified live at 0.785, 0.654 and 0.545) while the visible pill stays 20x14. Two traps: a Tailwind arbitrary-value utility (`size-(--kf-hit)`) resolves the variable where it is DECLARED, so it read the `:root` fallback of 1 and still measured 35px -- the value has to be referenced inline on an element inside the viewport; and the offset must scale with it (`calc(-22px / var(--kf-zoom, 1))`) or the pill drifts off the card edge as you zoom.
- **A bottom sheet on a phone gets 55dvh, not 70.** At 375x812, 70dvh is 568px of sheet against 244px of canvas -- and the header, demo banner and search box already own most of that, so the card you just tapped was itself covered. A detail panel that hides its own subject has lost the thing that makes it a panel rather than a page, since this one is deliberately non-modal so a person can be read against the family around them. 55dvh keeps 365px of canvas (the subject's row plus the one above it) and the sheet still scrolls to every section.
- **Collapse blocks the UNION, never the person, and that asymmetry is the data model showing through.** Parentage hangs off `unions`, so a mother's own outgoing edges are the PARTNER edges joining her to her partnerships -- block those and the couple comes apart, leaving a marriage rendered with one participant. Folding descendants therefore blocks the unions she partners in, which also means folding a mother's descendants folds the father's: they are the same children, and the union is the thing that says so. Upward is the opposite (a person's parent unions ARE their up-edge targets), so the block sits on the person. Found by a test that asserted both halves of the contradiction; see [lib/tree/collapse.test.ts](lib/tree/collapse.test.ts).
- **A collapse walk seeded from the ROOTS cannot fold ancestors, because the roots are what an upward fold hides.** The first implementation let every folded grandparent back in through the front door and an upward collapse silently did nothing. `entryPoints()` disqualifies anything behind a blockade and seeds from everybody else, so a fold stays LOCAL -- collapse one person in a tree of 117 and the other 116 are still entry points, where seeding from the collapsed node alone would leave a canvas holding one branch. The viewer and every collapsed node are anchors regardless, or folding your own ancestors empties the graph.
- **A union dot is the MARRIAGE, not a route to the children, so it survives a fold that hides them.** It is dropped only once fewer than two of the nodes it joins remain -- which is the single-parent case, where the dot would otherwise hang below the parent pointing at nobody.
- **Tailwind 4 scans markdown and CSS comments for class names, so documenting a broken utility COMPILES it.** The square-bracket gotcha note in this very file emitted a live `--tw-duration: --duration-base` rule into the production stylesheet (verified 2026-07-31 by grepping `.next/static/**/*.css`: 1 dead rule, traced to CLAUDE.md line 127, 0 after rewording). Describe a broken form in prose; never spell it.
- **`@theme` freezes a token's value; `@theme inline` emits the reference.** With two schemes on `[data-theme]`, a plain `@theme` copies whatever the attribute said at parse time into `:root`, so every utility is stuck on one scheme and switching does nothing. `@theme inline` compiles `bg-canvas` to `background-color: var(--kf-canvas)`, which resolves live. Verified in the built CSS rather than by looking: the utility must read `var(--kf-*)`, never a hex.
- **A light scheme is not an inversion, and two of its tokens are pinned by their floors.** Scored fresh against a warm off-white canvas: `ink-faint` at 4.77:1 is the last rung above the 4.5 text floor and `edge-past` at 3.24:1 the last above the 3:1 graphics floor, so neither can be quietened. The accent had to go DARKER, not lighter -- amber `#e0a33e` is 1.9:1 on white and invisible as a word -- hence `--color-accent-ink`, a separate token for the accent used as TEXT. Alphas are per scheme for the same reason (`--kf-taper-fade` is 0.68 dark / 0.82 light, both measuring ~3.3-3.5:1).
- **The motion switch is in the app, not `prefers-reduced-motion`, and that is deliberate.** These animations carry information -- the stagger shows generations assembling oldest first, the draw-on shows the skeleton growing parent to child, the pulse shows which way parentage runs -- so an OS flag set years ago to stop advertising banners jumping would silently delete a data channel. `data-motion="off"` on `<html>` is written by a discoverable, reversible control. The gate uses `0.01ms`, never `0`: a zero-duration animation never fires `animationend`, so anything awaiting it hangs.
- **The theme script must be a raw inline `<script>` in `<head>`, not `next/script`.** `beforeInteractive` still defers past first paint, which is exactly the white flash the script exists to prevent. It also needs `suppressHydrationWarning` on `<html>`, since it mutates two attributes before React hydrates -- a difference we cause on purpose.
- **Auth.js Drizzle adapter matches account columns by TS property name in snake_case.** `refresh_token`, `access_token`, `expires_at`, `token_type`, `id_token`, `session_state` stay snake_case in [lib/db/schema.ts](lib/db/schema.ts) even though the rest of the schema is camelCase. `expires_at` must be `integer` (OAuth epoch seconds), not a timestamp. Renaming them to camelCase produces a `DefaultPostgresAccountsTable` type error.
- **`experimental.useTypeScriptCli: true` in [next.config.mjs](next.config.mjs) is load-bearing.** TypeScript 7 removed the compiler API Next reaches for directly; without the flag dev boot throws "TypeScript 7.0.2 does not provide the compiler API required". Remove it once Next supports TS 7 natively.
- **pnpm 11 reads build-script approval from [pnpm-workspace.yaml](pnpm-workspace.yaml) (`allowBuilds:`), not `package.json`.** A `pnpm.onlyBuiltDependencies` field in package.json is silently ignored and installs fail with `ERR_PNPM_IGNORED_BUILDS`.
- **Dates are `date`, never `timestamp`.** A birthday has no timezone; storing it as an instant shifts people across midnight depending on who reads it. Fuzzy dates go in the separate `*Approx` text columns ("about 1890").
- **`unknown` is a real stored value**, not a missing one. Genealogy is mostly incomplete data and forcing a guess corrupts the record.
- **Only accepted links reach `fuseTrees()`.** A pending proposal must never change what anyone sees; callers filter on status.
- **A relation edge must never influence node placement.** `FlowEdge.layout` is the discriminator and [lib/tree/layout.ts](lib/tree/layout.ts) filters on it before handing edges to ELK. Feed a "friend" edge to the layered algorithm and that friend gets shoved into a lower generation, which silently misrepresents the family. [lib/tree/layout.test.ts](lib/tree/layout.test.ts) asserts the family skeleton's positions are identical with and without relation edges present -- if that test fails, the overlay leaked into the skeleton.
- **Withholding social edges from ELK creates a second problem, which `anchorFamilylessNodes()` in layout.ts solves.** A friend with no parents and no partner is an isolated node to ELK, so it lands in the FIRST layer and renders as somebody older than the grandparents. The post-layout pass moves those people onto the row of a contact they know. It deliberately runs after layout instead of as an ELK constraint, so the skeleton cannot shift to accommodate a friend.
- **Relation edges are `pointer-events: none` on themselves AND every descendant.** They render above the cards (`zIndex: 1001`) so their labels are not painted over, which means an edge label's `<rect>` sits on top of a card. React Flow sets `pointer-events: all` on labels, and that beats a `none` on the ancestor group, so the `*` selector in globals.css is load-bearing: without it a label swallows the drag that should move the card.
- **Hover BRIGHTENS the presence ring; it must not grow it.** The `.kf-lit` rule widened the ring by 7px on top of its resting spread, so a hub went 5px -> 12px (measured live) -- a 12px halo around a 168px card is not a highlight but a second border, an order of magnitude thicker than the card's own 0.67px hairline, and it pushes the card's apparent edge outward on a canvas where the gaps between cards carry meaning. Now +1px, with the whole signal in the colour: `--color-ink` at 65% composites to 7.63:1 against the resting ring's 5.10:1, a 1.50 step. That step was always what read as "this one"; the spread was only doing damage.
- **A lit family edge carries a travelling pulse, and it is a SECOND path rather than a dash on the first.** The base path is already animating its draw-on and taking colour and weight from the cascade, so layering avoids an override fight and keeps the line solid underneath instead of becoming a dashed line while a dash moves through it. `0.12 0.88` against a normalised `pathLength` is ONE bright segment chasing a long gap, not a train of dots -- a repeating pattern in motion reads as data flowing through a pipe, where one segment reads as the eye being led parent -> child. The offset animates 1 -> 0 so it runs downwards; reversed, it would assert that children produce their parents.
- **The pulse path is unconditional, and `stroke: none` is why that is free.** A `lit` prop on `FamilyEdge` would put focus state into the memo the layout effect depends on, re-running ELK on every hover -- the same trap the split edge arrays exist to avoid. So all 150 pulses are always mounted and CSS switches them on from the ancestor's `.is-active`. A path with no stroke is skipped at paint; 150 transparent-but-painted strokes would cost a compositor pass each. Verified live: idle pulses report `stroke: none` and `animation-name: none`, and a lit one steps `0.766 -> 0.549 -> 0.332` over two 300ms samples.
- **`aria-hidden` on an SVG `<path>` or `<g>` will not pass Biome, and the rule is right.** `noAriaHiddenOnFocusable` fires on both, and `focusable="false"` does not clear it. Do not suppress it: a bare `<path>` has no role and no accessible name, so there is nothing in the accessibility tree to hide, and the edge's name already comes from the `ariaLabel` React Flow puts on the group while `edgesFocusable={false}` keeps the subtree out of the tab order. The attribute was redundant, so it is absent rather than ignored.
- **A relation label is revealed by hovering the PERSON, not the edge.** Since the overlay takes no pointer events, focus comes from `onNodeMouseEnter`/`onNodeClick` in [components/tree/TreeCanvas.tsx](components/tree/TreeCanvas.tsx). Node focus is applied in its own effect that only rewrites `className` -- folding it into the layout's edge memo would re-run ELK on every hover, because the layout effect depends on that memo. Edge focus is no longer written to state at all: the rendered edge array is derived, so applying focus there too would store the same fact twice.
- **A revealed relation shows its label immediately; it does NOT wait for a second interaction.** The old rule started labels at `opacity: 0` until `is-active`, which was right when 52 relations were permanently drawn (52 labels would have been text over every card). But the reveal already consumed the hover and the tap, so there is no second gesture left to ask with -- and a line appearing with no word on it says a connection exists while withholding the one thing that makes it meaningful. The label fades in on a delay matching the draw-on, so the word lands as the line reaches the far card.
- **Directed relations are stored one way only.** "mentee" is not a stored value; it is the `mentor` row read from the other end via `relationLabel()`. Adding an inverse enum member would let the same fact exist as two rows with nothing to reconcile them.
- **Symmetric relations get id-sorted endpoints via `canonicalPair()`.** That is what makes the unique index able to reject a duplicate friendship recorded from either side. Directed kinds keep caller order, because A holds the role. Never insert a relation without going through `canonicalPair()`.
- **Self-relations are blocked in application code, not by a constraint.** Drizzle cannot express a CHECK inside an index, so `personAId <> personBId` is the caller's job. Fusion can also *create* a self-loop after a merge; `fuseTrees()` drops those.
- **Contact values never reach the canvas.** A card shows only which channels exist; a canvas gets screenshotted. Values default to `visibility: "tree"` (the narrowest) and require a deliberate click.
- **Phone numbers are stored as entered, never normalised.** Relatives abroad have country codes, older records have landlines, and rewriting the string loses information the owner deliberately typed. Dedupe compares trimmed + lowercased values only.
- **`next-env.d.ts` is excluded from Biome.** Next regenerates it with CRLF on every dev boot, so formatting it just loses the race. [.gitattributes](.gitattributes) pins LF for everything else.
- **React Flow error#004 ("parent container needs a width and a height") is not always noise.** While the container measures 0x0 React Flow never measures nodes, so edges render as an empty container. Framing keys off `useNodesInitialized`, not `requestAnimationFrame`, for exactly this reason.
- **`lib/db/client.ts` must stay importable with no `DATABASE_URL`.** Next collects page data by importing every route's module graph, so throwing at module scope fails `pnpm build` on a fresh clone. The client is always constructed for real and pointed at a placeholder URL whose queries throw a message saying what to do. A lazy Proxy is not an option: the Auth.js Drizzle adapter type-checks the instance it is handed at import time.
- **The session cookie is `kinfolk.session-token`, and the rename was a bug fix.** Auth.js defaults to `authjs.session-token`, and cookies are scoped by HOST, never by port -- so every Auth.js app on `localhost` reads and writes the same name. With `strategy: "database"` the stored token is a `crypto.randomUUID()` (see `@auth/core` `lib/init.js:77`), so a neighbour app running the JWT strategy leaves a 627-character JWE where a 36-character uuid belongs, and `/tree` throws `AdapterError` for a visitor who never signed in. The tell is a `session_token` param starting `eyJ` whose decoded header is `{"alg":"dir","enc":"A256CBC-HS512"}` -- that is a JWE, which the database strategy never mints, so the cookie cannot be ours. Only the session cookie is namespaced; @auth/core merges `cookies` over its defaults, so callback/csrf/pkce keep theirs.
- **A new account is provisioned in the `createUser` EVENT, not on page render.** [lib/tree/provision.ts](lib/tree/provision.ts) gives every new user a graph holding one node (themselves, `claimedByUserId` set, `verification: "self_confirmed"`, `sex` left `unknown`). It fires once per account lifetime inside Auth.js's own flow; doing it in `TreePage` would re-derive "is this the first visit" from the data on every render. It swallows its own errors and is idempotent on an existing tree, because a retried OAuth callback must not cost somebody their session or leave them two graphs -- `EmptyTree` is the correct screen if it fails. Never derive `sex` from the display name: it is a STORED value, so unlike a kinship term a guess outlives the render that made it.
- **Pages call `sessionOrNull()`, never `auth()` directly.** Sessions live in the database, so with no `DATABASE_URL` there is nothing to look one up in and Auth.js logs `MissingSecret` on every render. Reading the demo tree needs no auth, so the guard belongs in one place.
- **`DATABASE_URL` in `.env.local` must be the DIRECT host, not the `-pooler` one.** The app talks to Neon over their serverless HTTP driver, which is happy either way, but `drizzle-kit push` opens a plain TCP connection that the pooler endpoint will not serve. One variable feeds both, so the direct host is the only value that satisfies both readers.
- **`drizzle-kit push` on Windows prints `Changes applied` and THEN crashes** with `Assertion failed: !(handle->flags & UV_HANDLE_CLOSING)` and exit code 3221226505. That is libuv tearing down the websocket after the work has committed, not a failed migration. Confirm against `information_schema` rather than trusting the exit code, which is why `pnpm db:smoke` exists.
- **`view.kinship` is a `Map`, not a record.** `kinship[id]` type-checks (index signatures on a Map object) and returns `undefined` for every id, so an assertion written that way passes vacuously against an empty expectation. Always `kinship.get(id)`.
- **An accepted link is symmetric, so the FAR tree's owner loads your tree too.** Their `loadTreeView()` reports `trees: 2`, not 1 -- that is the product working, and the invariant to check is that the far tree arrives at `linked` access with its tree-private contacts stripped, not that it is absent.
- **`tsx` compiles a bare `.ts` script to CJS here**, because package.json has no `"type": "module"`, so top-level `await` fails with "not supported with the cjs output format". Name a script `.mts` to get ESM.
- **Only the INNER card animates on entrance, never the node wrapper.** React Flow owns the wrapper's `transform` for positioning; animating it fights the layout and the node lands in the wrong place. Hence `.kf-enter > *` in globals.css rather than `.kf-enter`.
- **Import `getNodesBounds` from `useReactFlow()`, not the package root.** The standalone export has no node lookup, cannot handle sub-flows, and warns on every single call.
- **The fusion reveal reads `contributingTreeIds.length`, so it is a property of the data, not a flag.** Mine-only mode produces `merged 0` and therefore no stacked sheets, automatically. The sheets carry no `z-index`: they and the card are all `z-index: auto`, so paint order alone puts the card on top, and that survives an ancestor gaining a stacking context in a way a negative index would not.
- **Generation bands come from person nodes only.** A union dot sits between two rows, so including one invents a half-generation. The entrance stagger therefore snaps each node to its NEAREST band rather than an exact y match, or every union dot gets delay 0 and pops in ahead of the couple it joins.
- **A Tailwind 4 CSS variable in an arbitrary value needs PARENTHESES, not brackets.** `duration-(--duration-base)` compiles to `var(--duration-base)`; the square-bracket form emits the literal property name instead, which is not a valid duration, so the property silently falls back to its initial value and the transition simply does not happen. Nothing warns -- not the build, not Biome, not the browser console. 34 utilities across this repo were dead this way; when adding one, confirm the computed style on a real element rather than trusting the class list. **Do not write the broken form out in prose anywhere in this repo, including this file and CSS comments**: Tailwind's scanner reads markdown and comments as class-name sources, so spelling it literally compiles a dead rule into the production stylesheet -- verified 2026-07-31, this very line was doing it.
- **`color-mix()` cannot be contrast-scored from `getComputedStyle`.** It computes to an `oklab()` string, so any sRGB parse of the value fails or silently reads garbage. Composite the pair on a real 2D canvas and read `getImageData` instead -- that is how the lattice dot's 1.14:1 and the hairline's 1.34:1 were measured.
- **Feeding React Flow's own CSS variable beats overriding its selector.** Their `.react-flow__background-pattern.dots { fill: ... }` ties a `.react-flow .react-flow__background-pattern` override on specificity and then wins on source order, because their stylesheet is imported after globals.css. Setting `--xy-background-pattern-color` on `.react-flow` lands, since their rule reads it. This also means the `color` prop on `<Background>` must be REMOVED, not just left unset: it writes `--xy-background-pattern-color-props`, which they check first.
- **`.react-flow__background` renders OUTSIDE `.react-flow__viewport`.** The pane carries the pan transform and the background does not (confirmed on a live element), which is exactly what lets the edge-fade `mask-image` stay screen-fixed while the tree pans under it. Anything else placed in that SVG inherits the same non-panning behaviour.
- **The sibling bar is computed from POSITIONS, after ELK, never as an edge.** ELK routes parent-child edges individually, so twelve children produce twelve separate diagonals; the bar is the thing that makes them read as one family. Lanes are assigned widest-span-first and shared between families that cannot overlap in x, which is what keeps a generation to a single clean line -- [lib/tree/siblings.test.ts](lib/tree/siblings.test.ts) asserts `barCollisions()` is 0, because two families sharing a y AND an x range is the one way the bar can lie about whose child is whose.
- **A bar can never sit above its own union dot.** With a tight generation gap the lane offset exceeds the room available, and the drop line then points UPWARDS, reading as the children being the ancestors. `siblingBars()` clamps to just below the dot; there is a test pinning the clamped value.
- **Kinship is walked from the graph, never guessed from `sex`.** `sexEnum` includes `"other"` and defaults to `"unknown"`, so `kinship.ts` returns neutral terms ("parent", "sibling") when the stored value cannot name a gendered one. Guessing to get a nicer word would assert something nobody recorded, and it is also why the gender-required layout libraries were rejected.
- **An inferred kinship is drawn a step fainter than a proven one.** `via: "in_law"` and `via: "relation"` are read off a partner's line or a stored relation rather than proven by the ancestor walk, so they get `text-ink-faint` where a walked term gets `text-ink-muted` -- the same how-firmly-drawn-tracks-how-well-known hierarchy as the provenance tick.

## Repo-specific rules

- Design follows the `design` skill's taste-2026 module: near-black canvas (never `#000`), monochrome token stack plus ONE accent (warm amber, deliberately not product blue), 1px hairlines instead of heavy shadows, mono + `tabular-nums` for metadata and numbers, 44px minimum hit targets, ease-out under 300ms, mobile-first.
- **Glass (`.kf-glass`) is only for chrome that FLOATS over the canvas, and the boundary is performance, not taste.** `backdrop-filter` forces a compositor layer and re-filters what is behind it every frame; on 117 cards that is 117 layers re-rasterising as the tree pans, which is the "1000+ members without lag" target broken by decoration. At most five are on screen. Cards get a hairline plus one soft shadow on hover -- hairlines remain the primary boundary everywhere.
- **Colour is declared per scheme and consumed by NAME. No component carries a `dark:` variant.** Add a colour by declaring it in both `[data-theme]` blocks and exposing it through `@theme inline`. A one-scheme token is a bug that only shows up for half the users.
- Keep graph maths in `lib/tree/` with no React or DB imports so it stays unit-testable. Every fusion change needs a test in [lib/tree/graph.test.ts](lib/tree/graph.test.ts). Collapse and the panel's family roles are in that layer for the same reason: [lib/tree/collapse.test.ts](lib/tree/collapse.test.ts) and [lib/tree/relatives.test.ts](lib/tree/relatives.test.ts) both caught defects invisible on screen, because a person who vanishes from a canvas does not announce that they were dropped for the wrong reason.
- **A keyboard shortcut and its help row come from ONE array** (`BINDINGS` in [components/tree/TreeShortcuts.tsx](components/tree/TreeShortcuts.tsx)). A handler in one file and a documented list in another drift on the first change, and a help sheet that lies is worse than none. Single letters need the typing guard: without it, typing a name into search zooms, fits and cycles the detail level on the way through.
- Fused ids must be deterministic (smallest member id) so output never depends on input order. There is a test for this; do not "optimise" it away.
- Relation categories are distinguished by **dash rhythm, not colour** (kin `8 3`, care `9 3 1 3`, social `5 4`, professional `2 4`, other `1 4` -- see [app/globals.css](app/globals.css)). Colour-coding them would break the one-accent rule. All five have an explicit rule, ordered tightest rhythm to sparsest so the dash reads as distance from kinship; each rule sets ONLY `stroke-dasharray`, since weight belongs to closeness and colour to `--color-edge-soft`.
- **Every rhythm lives in a `--kf-dash-*` token, because two readers depend on it**: the edge rules and the legend's sample lines. Hardcode it in both and the next change lands in one of them, leaving the key describing a line the canvas no longer draws -- the one failure a legend cannot survive, since its whole value is being believed without checking. The active-relation rule is the deliberate exception and says so inline: its literal `5 4` is coupled to the `-18` dashoffset so the flow animation loops seamlessly.
- **The legend is census-driven, so a row never explains a mark that is not on this canvas.** [lib/tree/census.ts](lib/tree/census.ts) counts the ENABLED nodes and edges (the caller passes `visibleEdges()`, so switching the overlay off empties the relation rows) and [components/tree/TreeLegend.tsx](components/tree/TreeLegend.tsx) drops any row whose count is zero. Deliberately the enabled set rather than the momentarily-rendered one: relations are revealed one person at a time, so a census over what is literally on screen would empty every relation row the instant the pointer left a card -- a key that blanks itself while you read it. The counts answer "what is in this graph"; the Connections section's `note` answers "when will I see it", which is the row a reveal-based canvas cannot do without. Kinfolk knows 17 relation kinds and 5 verification levels and no real tree uses all of them; one row pointing at a line nobody can find costs the whole key its credibility. Rows are derived from `RELATION_KINDS`, the dash tokens, and `PROVENANCE` rather than restated.
- **A card encoding listed in the legend must be reproduced with the card's own structure, not approximated.** `.kf-presence` is `position: absolute; inset: 0` with its own `border-radius`, so a bare span wearing that class escapes its row and pins to the panel corner, and its radius beats any Tailwind `rounded-*` (plain CSS outranks a utility layer). Wrap it in a `relative` parent and pass the radius through `style`, the way [components/tree/PersonNode.tsx](components/tree/PersonNode.tsx) does. Verify a sample by reading its rect off a real element -- both bugs looked correct in the file.
- A new relation kind means three edits, in this order: the `relationKindEnum` member, its `RELATION_KINDS` spec (label, inverse, symmetric, category), and its `.is-<kind>` selector added to that CATEGORY's rule in globals.css. Never a rhythm of its own -- the rhythm names the category, so a per-kind dash would claim a distinction the legend does not make. Skip the spec and `relationLabel()` throws on read.
- **Write permission is [lib/tree/authz.ts](lib/tree/authz.ts), NEVER `accessibleTrees()` from load.ts.** The read helper grants `member` to anyone with a row, which is correct for reading and catastrophic for writing: it would let a `viewer` grant edit, and it would let a tree reached through an accepted person link be rewritten by the other family. An accepted link means "we agree this is the same human", not "you may edit my records". `editableTreeIds()` requires ownership or an `owner`/`editor` grant. Verified live: a user cannot edit another user's graph, and `assertSameTree()` refuses a cross-graph pair with a message pointing at person links.
- **A relation or union may never straddle two trees.** `assertSameTree()` enforces it, because `person_relations` and `unions` have nowhere to record the other family's consent -- that is what `person_links` is for. Without the check, one user could unilaterally write an edge into somebody else's graph.
- **`editableTreeId` on the view is a RENDERING hint, not a permission.** It decides whether the Add panel is drawn (null in demo mode and for a read-only viewer, which hides the editor rather than disabling it -- a disabled control advertises an action that can never work). Every action re-checks server-side, because a value that reached the client is a value the client can change.
- **The editor pre-fills its "from" field from the canvas selection, and SAYS so in the header.** Clicking a card already sets hover focus, so `onNodeClick` carries both. Without the header naming the picked person the select appears to change on its own, which reads as a bug rather than a shortcut. Union dots are skipped: a junction is not somebody you can relate to, and reporting one puts "Unknown" in a picker.
- **Every full-page screen wears `.kf-lattice` and opens with `.kf-chip`, both ported from `brand/portfolio-react`.** The landing, sign-in and empty-state pages were type on an empty near-black field, which reads as unfinished rather than as restraint -- their hero solves it with a masked dot texture (`.grid-bg`) and a pill chip before the headline. The lattice is pitched at **24px to match the canvas's own `<Background gap={24}>`**, which is the point: a visitor meets the texture on the landing page and then pans across the same one in the graph, instead of watching it change pitch. Masked off-centre at `50% 38%` so the brightest part sits under the headline rather than in the empty lower half.
- **The landing headline puts the accent on the SECOND line only.** The product is the join -- two families' records meeting without either being overwritten -- so the amber lands on the three words that say it, once. A gradient across both lines was the obvious move and is wrong: it spends the accent on decoration, and the one-accent rule exists because amber has to keep meaning "you" and "this relation" on the canvas.
- **Card width AND height both come from `NODE_METRICS`, because ELK reserves both.** `PersonNode` set only the width, so the card sized itself to content -- raising the reserved height to fit a two-line kinship term then bought nothing on screen and left the layout and the card disagreeing by 16px (reserved 92, rendered 78, measured live). The inner card needs `size-full` for the same reason.
- **The kinship line clamps to TWO lines; the name never wraps.** Measured on the sample tree: 31 of 117 kinship terms (26%) were truncated at one line, because that term is the widest thing on the card -- "great-great-uncle by marriage" needs 164px in a 142px column, where the p90 NAME needs 109px. Truncating kinship is worse than truncating anything else, since the terms share long prefixes and "great-great-gran..." could be a grandmother or a grandfather. `kinship.ts` is already maximally compressed (greats collapse to `4x great-` past three), so the fix belongs in the card.
- **Do NOT put a glyph on the name line.** Tried, measured, reverted: the sex glyph plus its gap takes the name column from 142px to 105px and pushes 9 of 117 names from fitting into truncating. The name is the one thing on a card that must never be clipped. Glyphs that are on EVERY card go on the metadata row; the name line carries only conditional marks (provenance tick, conflict shield).
- **A screenshot catches what per-element measurement cannot.** The presence ring was 80% of `--color-edge` (5.12:1) and read fine in isolation -- but 96 of 117 people clear the ring floor, so four cards in five wore a grey halo and the canvas read as fog with cards in it. Now 28% (1.60:1, just above the 1.26:1 hairline) and capped at 6px spread rather than 10. The old note justified the weight by calling the ring "the only thing that says how connected somebody is"; it is not, the converging edges say it too, and more precisely.
- **A relation is REVEALED for one person at a time, never drawn at rest, and this replaced the whole `is-far` mechanism.** Measured on the sample graph: the 52 relation edges were 73% of all edge ink at a median span of 2214px, against the family skeleton's median of 69px (32x) -- and the data is sparse, since the median person has ONE relation and 56 of 120 have none. Fifty-two permanent canvas-crossing diagonals were the haze the cards sat in, and distance-fading them (`--color-edge-far`, `FAR_SPAN`, `#kf-taper-far`) was treating a symptom: the defect was drawing a per-person fact globally. `revealedRelations` in [components/tree/TreeCanvas.tsx](components/tree/TreeCanvas.tsx) filters to the hovered-or-pinned person, so the resting canvas is the family skeleton at ONE stroke treatment (verified live: 150 edges, 1 treatment, down from 202 edges and 15). All three far-edge machineries are deleted rather than left unreferenced -- a revealed edge is drawn at full strength however far it reaches, because the viewer asked for precisely that line.
- **The reveal is split across TWO edge arrays, and the split is what keeps ELK off the hover path.** `familyEdges` is state written once per layout; `relationFlowEdges` is a memo over the revealed person; the rendered array is a memo merging both. The family memo must read `enabledEdges`, NOT the revealed set -- the layout effect depends on it, so a memo that narrowed with the pointer would re-run ELK for the whole graph on every mouse move. Same trap as the focus effect, reached from a different direction.
- **Hover reveals, click PINS, and the pin is not a nicety.** A hover-only reveal vanishes the moment the pointer moves towards the line it just drew, which on a canvas this wide makes a long relation impossible to follow -- and on a phone there is no hover at all, so the tap is the only way in. `pinnedId ?? focusedId` is the revealed id, clicking the same card again unpins, and `onPaneClick` clears both. Search pins too: there is no pointer on a card you travelled to, and "who is this person connected to" is usually why you searched them. `lit` keys off the REVEALED id, not the hovered one, or a pinned person's lines would sit on screen with nothing lit and every card dimmed around them.
- **The card's pointer-tracked wash writes CSS custom properties, never React state.** Ported from `brand/portfolio-react`'s `GlassCard`, with three deliberate departures: its `useState` + rAF pair re-renders on every pointermove, which React Flow answers by re-measuring the node -- ruinous across 117 of them, so `--kf-mx`/`--kf-my` are set directly on the element; its 3D tilt is dropped, because React Flow owns the wrapper's `transform` for positioning; and its `useReducedMotion` gate is dropped, which that repo's own CLAUDE.md forbids in new code. The wash is accent at 8% (1.13:1) -- texture, not information, which is the only thing allowed to use the accent decoratively.
- **Stroke weight is ONE scale, in `--kf-stroke-*` tokens, and four readers depend on it** (the skeleton rule, the base relation rule, the three closeness rules, and the legend's sample lines). Before this they each named their own number and had already drifted: the base relation rule said `1` while `is-close-1` said `0.75`, so an edge's weight depended on whether its closeness class had matched, and 0.75 lost its dash rhythm entirely below about 0.8 zoom -- the channel saying "acquaintance" was destroying the channel saying which KIND. Now faint 1.1 / soft 1.5 / firm 1.9 / skeleton 2.3 / close 3, evenly spaced so the scale is learnable.
- **The closeness scale is centred ON the skeleton weight, and only because relations are revealed.** It used to be capped under 2.3 at every step so an always-on relation could never outweigh a parentage. A revealed relation is not competing with the skeleton -- it is the answer to a question just asked, and the hierarchy is established by the resting canvas -- so it now runs soft 1.5 / skeleton 2.3 / close 3. Restore the always-on overlay and this inverts back into a lie.
- **The accent is spent on revealed relations, and reclaiming it from the skeleton was the second measured defect.** `.is-partner` was `--color-accent-dim`, so **68 of 150 family edges rendered amber** (`rgb(138,101,38)` live) -- nearly half the skeleton wearing the one colour reserved for "you" and "this relation", which is not an accent but a theme. A partnership needs no colour: it is the one family edge running HORIZONTALLY, so its geometry distinguishes it for free at every zoom. The rule survives only to set `stroke-linecap: butt`, which makes the horizontal run meet its drop lines squarely where the skeleton's round cap bulges past the join.
- **Direction is a tapered stroke (`#kf-taper`), never an arrowhead.** `MarkerType.ArrowClosed` was removed for three independent reasons: a 14px triangle on a 400px bezier lands where the line meets a card and reads as part of the card's border; React Flow hoists markers into a shared `<defs>` and writes the colour as an INLINE style, so the head could not inherit dimming, the active state or the past colour (a dimmed edge kept a full-contrast head); and it was redundant with the dash flow, which is legible along the whole line. The gradient must use `gradientUnits="objectBoundingBox"` so ONE def serves paths running in every direction -- `userSpaceOnUse` would need per-edge coordinates. `is-ended` overrides the `url()` reference rather than the colour, because a gradient stroke cannot be recoloured. `var()` DOES resolve inside `<stop stop-color>` (verified on a live element). Both stops are now `--color-accent`, matching the revealed relation's own stroke -- a taper fading to a different hue than the line it belongs to reads as two marks rather than one line arriving.
- **A gradient's faint end has to be contrast-scored on the COMPOSITE, like any other alpha.** The taper first faded to 35%, which composites to 1.69:1 on the canvas -- under the 3:1 SC 1.4.11 owes, and exactly the defect this repo's own contrast rule exists to catch. 0.68 measures 3.28:1 and still reads as a taper, since 5.90 -> 3.28 is a 1.8x drop. Never fade an edge to 0: the terminus is where a reader looks to see who the relation lands on, and a stroke reaching transparent reads as cut off rather than arriving.
- **`--color-edge-soft` is 5.90:1, raised from 4.03:1, because the overlay is CONTENT.** Kinfolk is a contact graph as much as a pedigree, so a friendship is not an annotation on the skeleton -- and at 4.03 with a 0.75px stroke it was the faintest mark on the canvas carrying information nothing else carried. The gap to `--color-edge` (7.50:1) is still the hierarchy at 1.27x, with weight carrying the rest. Now used only by the taper's fallback readers, since a revealed relation strokes in the accent.
- **There is deliberately NO `.is-relation.is-active` rule, and its deletion is load-bearing.** It recoloured a lit relation to the accent, raised its weight, and looped a 700ms dash flow -- all to pick one line out of fifty-two. Now that relations are revealed, `is-active` matches every relation on screen, so the rule would say "this one" about all of them. Worse, its literal `stroke-dasharray: 5 4` overrode the category rhythm (destroying the only channel that separates a mentorship from a friendship, exactly when the viewer asked to see it) and its infinite animation would put every revealed line into perpetual motion -- the "fifty animated edges is a screensaver" failure, arrived at from the other side.
- **Counting an enum into a `Record` needs a fallback even when the column is `notNull`.** `census.ts` is pure and counts whatever it is handed, and `sex[undefined]++` does not throw -- it silently widens the record with an `"undefined"` key holding `NaN`, which the legend then tries to render as a row for a mark that does not exist. Hence `sex[person.primary.sex ?? "unknown"]++`, with a test that pins the key count at 4.
- **Contrast is a measurement, not a taste call.** Text owes 4.5:1 (WCAG SC 1.4.3) and an edge, ring or arrowhead owes 3:1 (SC 1.4.11) against the surface behind it, so anything drawn with `opacity` has to be scored on the COMPOSITE (`fg*a + bg*(1-a)`) rather than on the token. That is why closeness is stroke weight only, an ended relation gets `--color-edge-past` instead of a fade, and the `.kf-dim` rules sit at 0.5 / 0.6 rather than the 0.28 / 0.25 that took a dimmed name to 2.29:1. Prefer a second token over an opacity: a value can be checked, a composite has to be recomputed every time the backdrop moves.
- **Edge colour is two tokens, and both were verified in the browser rather than in the file.** `--color-edge` (7.50:1) is the family skeleton, `--color-edge-soft` (4.03:1) the relation overlay. The skeleton rule is `.react-flow .react-flow__edge-path`, doubly qualified on purpose: React Flow's stylesheet is imported after globals.css, so a single-class rule loses on source order and the skeleton silently renders in their `#b1b1b7` default. Any new React Flow override needs the same treatment -- read the computed style off a real element to confirm it landed, since the file will look correct either way.
- **The layout stack is elkjs + React Flow, and the alternatives were measured rather than assumed** (2026-07-29, versions live from the npm registry). Do not swap one in without re-running this: `family-chart` (3.5k weekly) and `relatives-tree` (2.1k) both require a binary `gender`/`Gender` on every node, so adopting either means corrupting a record whose `sexEnum` is `["female","male","other","unknown"]` and defaults to `"unknown"` -- and neither models non-family relations, which is half of what Kinfolk is. `d3-flextree` is a strict tree (one parent per node) and last published 2021-11-08; a family tree is a DAG. `d3-dag` 1.2.2 is the one real contender (DAG-native, variable node sizes, 56k weekly) but it is synchronous on the main thread with no edge routing, so it trades ELK's worker and port routing for nothing we lack. `sigma`, `cytoscape`, `g6` and `@cosmograph/cosmos` (still `2.0.0-beta.20`, 2024-12-19) are force-directed network renderers built for thousands of nodes, which is the opposite of a generation-banded pedigree. Already on the latest `elkjs` 0.12.0 and `@xyflow/react` 12.11.2.
- **`react-tree-graph` was evaluated on 2026-07-29 and rejected, on the same grounds as `d3-flextree`.** Registry facts, not memory: 8.0.3, published 2025-01-13, 3.7k weekly, built on `d3-hierarchy` (pinned `^2.0.0`, a full major behind the current 3.1.2 from 2022). `d3-hierarchy` is "layout algorithms for visualizing HIERARCHICAL data" -- a strict tree, one parent per node. A Kinfolk graph is a DAG: a child belongs to two unions (birth and adoptive), parentage hangs off `unions` precisely so remarriages and half-siblings work, and half the product is non-family relations that carry no generation at all. Feeding that to a strict-tree layout means either dropping the second parent or duplicating the node. It also has no edge routing, no port model and no non-family edge concept, so it cannot express the sibling bar, the relation overlay, or `anchorFamilylessNodes()`. The name matches what Kinfolk looked like three commits ago; it does not match what the schema models.
- **Never send this repo's content to an external LLM API.** It is private and the files carry family data shapes. The graphify run here is local-AST-only for exactly this reason (0 tokens, no key), and the Gemini semantic pass stays off. `graphify-out/` is gitignored.
- Private repo, so no Renovate.

## Demo mode

Sample data is reachable before auth exists, following the ledger-sync pattern: ONE UI, two data sources, a flag, and mutation guards. The difference is that Kinfolk renders on the server, so the flag is an httpOnly cookie read in a server component rather than a client store -- which also keeps `lib/tree/sample.ts` out of the client bundle entirely.

- Both paths produce the same `TreeView` ([lib/tree/view.ts](lib/tree/view.ts)), so no component knows which one it is rendering.
- [lib/tree/demo.ts](lib/tree/demo.ts) calls the real `fuseTrees` and `toFlowGraph` rather than shipping pre-computed positions. If fusion breaks, the demo must break too; a demo that cannot fail is a screenshot, not a proof.
- Mine-only mode drops the other tree AND its links, so it is a genuinely smaller dataset rather than the same tree with nodes hidden. That is what a viewer without a share grant would actually get.
- A real session beats the demo cookie, so signing in from inside the demo shows your own (possibly empty) tree instead of silently keeping sample data on screen.
