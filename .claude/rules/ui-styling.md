# Colour, contrast, themes and motion

Moved verbatim from `CLAUDE.md` on 2026-10-31. Loads when a file matching `paths:` is read or edited.

## Gotchas

- **Vite inlines any asset under 4 KiB as a `data:` URI, and the SPA's CSP allows fonts from `'self'` only.** JetBrains Mono's Cyrillic Extended subset is 2028 bytes, so until 0.6.1 every Pages load logged a `font-src` violation and that face could never load. Nothing else showed it: `pnpm --dir frontend dev` never inlines, and the Next fallback emits fonts as files under a policy that allows `data:` fonts. `build.assetsInlineLimit` in [frontend/vite.config.ts](frontend/vite.config.ts) opts font files out; keep it that way rather than adding `data:` to `font-src`. After adding a font or a subset, check a production build's CSS for `data:font` -- it must be 0.
- **The MAJORITY state gets no colour, on every surface that draws it.** 94 of 117 people in the earlier sample tree were living, so a green living-rail put a saturated 7.36:1 stripe on 80% of the cards -- brighter than the NAME above it (rail luminance 0.366 against the card's 0.0065) -- and at fit zoom the tree read as rows of green dashes rather than as a family. The same fact wearing the same colour appeared three times: the card rail, 93 of 152 minimap rects, and 93 of 117 dots in dot mode, where one amber pixel for the viewer had to compete with a green mass. Living is now unpainted (card), `--color-edge` (minimap and dots); deceased keeps the quiet grey because it was the minority there (23; in the current Wikidata sample all 228 records are deceased), and `unknown` keeps a faint ink mark because an unrecorded status is a real stored value (it wore the hairline until 0.8.0, which measured 1.92:1 light and 2.02:1 dark against the 3:1 floor). The profile avatar and its relative rows follow the same rule since 0.8.0: living is neutral there too, where it used to tint everybody not deceased green, "not recorded" included. Every individual green cleared its contrast floor -- only the screenshot showed that 94 of them shared a canvas, which is the same lesson as the presence-ring fog reached from the other side.
- **globals.css is unlayered, so its `.kf-*` rules beat every Tailwind utility on the same element.** A `bg-surface-raised` beside `.kf-header-control` never applied (pressed toggles now style `[aria-current]` and `[aria-pressed]` in the CSS), `kf-primary-action` turned the profile form's tinted Save into the landing page's button, and `.kf-index-card__name` overrode the card name's size and weight utilities, which 0.8.0 removed rather than let them pretend. A utility on a `kf-*` element that has to win needs the `!` suffix (the segmented-group focus rings use `focus-visible:-outline-offset-2!`).
- **New `:hover` rules in globals.css go inside `@media (hover: hover)`.** Tailwind's `hover:` utilities are gated already; the hand-written rules were not, so on a touch screen the last thing tapped kept its hover state -- a pressed `+` stayed lit and scaled up after its strip had closed, and tapped cards kept their wash and 3D lift.
- **`@theme` freezes a token's value; `@theme inline` emits the reference.** With two schemes on `[data-theme]`, a plain `@theme` copies whatever the attribute said at parse time into `:root`, so every utility is stuck on one scheme and switching does nothing. `@theme inline` compiles `bg-canvas` to `background-color: var(--kf-canvas)`, which resolves live. Verified in the built CSS rather than by looking: the utility must read `var(--kf-*)`, never a hex.
- **A light scheme is not an inversion.** The current palette uses near-black `#0b1012` in dark mode and separate light surfaces, with blue accents and scheme-specific ink, edge, and alpha values. Keep `--color-accent-ink` separate because a hue usable as a line is not automatically usable as small text. Re-measure text against 4.5:1 and meaningful graphics against 3:1 whenever a canvas, surface, token, or alpha changes. The warm-paper, evergreen, and amber palette belongs to 0.3.0; its contrast measurements do not validate 0.4.0.
- **Motion has an explicit Full/Reduced choice in Appearance.** Full is the default; the saved choice, rather than an OS motion preference, controls `data-motion` on `<html>`. Reduced freezes decorative CSS sequences, suppresses Motion transforms, and removes animated canvas travel while keeping every action available. The CSS gate uses `0.01ms` to preserve animation completion behavior; imperative viewport travel uses zero duration.
- **The theme script must be a raw inline `<script>` in `<head>`, not `next/script`.** `beforeInteractive` still defers past first paint, which is exactly the white flash the script exists to prevent. It also needs `suppressHydrationWarning` on `<html>`, since it mutates two attributes before React hydrates -- a difference we cause on purpose.
- **Hover BRIGHTENS the presence ring; it must not grow it.** The `.kf-lit` rule once widened the ring by 7px on top of its resting spread, turning a highlight into a second border and pushing the card's apparent edge into layout space. It now adds only 1px; the theme's lit colour carries the signal. Keep that colour visibly stronger than the resting ring in both schemes and re-measure after palette changes.
- **`color-mix()` cannot be contrast-scored from its source token or a naive sRGB parser.** Browsers may expose the computed value as `oklab()`, and translucent glass, lattice, wash and ring marks depend on the surface behind them. Resolve the actual pair through a 2D canvas and read `getImageData`; re-measure after either scheme's token or alpha changes.

## Repo-specific rules

- **Floating chrome stays opaque.** The existing `.kf-glass` class no longer applies backdrop blur. Avoid re-filtering the moving graph behind toolbars or cards; borders and restrained shadows provide separation without adding a compositor layer per person.
- **Colour is declared per scheme and consumed by NAME. No component carries a `dark:` variant.** Add a colour by declaring it in both `[data-theme]` blocks and exposing it through `@theme inline`. A one-scheme token is a bug that only shows up for half the users.
- **Public entry screens use [components/ui/BrandFrame.tsx](components/ui/BrandFrame.tsx).** Next and Vite pass runtime-specific auth/demo actions into the same family-atlas header, hero, relationship illustration, and privacy copy. Sign-in uses the compact form of that shell. Keep the public screens and authenticated workspace on the same typography, palette, and appearance controls.
- **The landing headline accents "One family atlas." in blue.** Keep the preceding "Your people. Their stories." lines in the primary text color. Use the shared accent treatment without gradient text; canvas accents identify the viewer, selection, and revealed relationships.
- **A screenshot catches what per-element measurement cannot.** The presence ring once read acceptably in isolation but appeared on most people, turning the full canvas into fog. It now uses a quiet scheme-specific alpha (`--kf-ring-alpha`) and a capped 6px spread rather than 10. The converging edges already express connection density more precisely; the ring must remain texture, not a second card border.
- **Contrast is a measurement, not a taste call.** Text owes 4.5:1 (WCAG SC 1.4.3) and an edge, ring or arrowhead owes 3:1 (SC 1.4.11) against the surface behind it, so anything drawn with `opacity` has to be scored on the COMPOSITE (`fg*a + bg*(1-a)`) rather than on the token. That is why closeness is stroke weight only, an ended relation gets `--color-edge-past` instead of a fade, and the `.kf-dim` rules sit at 0.5 / 0.6 rather than the 0.28 / 0.25 that took a dimmed name to 2.29:1. Prefer a second token over an opacity: a value can be checked, a composite has to be recomputed every time the backdrop moves.
