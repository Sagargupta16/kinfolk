# Canvas state and interaction

Moved verbatim from `CLAUDE.md` on 2026-10-31. Loads when a file matching `paths:` is read or edited.

## Key files

- [components/tree/FeedPanel.tsx](components/tree/FeedPanel.tsx) -- the feed rail, wearing the detail panel's own shell (bottom sheet on a phone, right rail on a desktop); a row travels to its person and opens their panel, and the feed waits underneath
- [components/tree/TreeStage.tsx](components/tree/TreeStage.tsx) -- owns Tree / People navigation, Options, and `viewedId` above the keyed React Flow provider; persists the viewed person's source ids so search, feed, cards, LOD, arrangement, and view scope share one subject

## Gotchas

- **Escape dismissal is one LIFO stack, not one window listener per panel.** [components/tree/escape.ts](components/tree/escape.ts) owns the mounted surface order, so one Escape closes only the top account/search/legend/editor/share/feed/detail surface. A new dismissible overlay registers there; adding its own `keydown` listener recreates the multi-close bug and makes mount order observable.
- **CSS-only canvas state must never enter the ELK layout dependency graph.** Depth, pointer capability, focus, dim and lit are class rewrites, not geometry. [components/tree/TreeCanvas.tsx](components/tree/TreeCanvas.tsx) keeps layout on data/arrangement/detail inputs, reapplies classes after `layoutEpoch`, and updates draggable state separately. A new object/array dependency must have stable identity or a hover/toggle can re-run layout and move the viewport.
- **Social links is client state; All trees is a navigation.** The server always sends every edge (layout needs the relations), so hiding them only changes what is drawn: `TreeStage` holds it and mirrors it into the URL with `replaceState`. It was a link, which refetched the tree, reran ELK and dropped every fold and the zoom -- in the SPA a full document reload. Mine-only really fetches less, so it stays a link, built from the current state (`demo=1`, `relations=0`) so it carries both.
- **The current subject is `viewedId`, not React Flow selection, the open detail id, the relation pin or the signed-in self.** [components/tree/TreeStage.tsx](components/tree/TreeStage.tsx) owns it above the provider keyed by arrangement and LOD; search, feed, cards and the history docket all update that one value. The canvas derives its `Viewing` ticket, trail, collapse anchor, framing target and orbit centre from it. `selfId` remains a quieter identity marker and gets a separate `You` travel control only when it differs. A fused id is not durable across a full SPA navigation: mine-only Edward VII is `v-Q20875` while the combined view calls him `c-Q20875`, so the stage stores his contributing source ids under `kinfolk.viewed-sources` in `sessionStorage` and resolves the best matching fused person after each load. Persisting only `viewedId` silently resets the subject when the view boundary changes.
- **Phone chrome needs disjoint pointer lanes, not only different z-indexes.** Search sits in the workspace toolbar above the canvas rather than floating over it, the viewing docket takes the canvas's upper-left corner, and the overview and travel buttons sit bottom-right, opposite React Flow's zoom controls. Detail framing measures the real panel and docket rather than assuming one fixed inset. On a phone the docket is removed from layout (`hidden`) while the detail sheet is open; remove or `visibility: hidden` chrome the same way, because opacity plus pointer blocking alone would leave invisible controls in keyboard and switch-navigation order. A higher transparent or glass panel still intercepts a real click even when the control beneath is visibly unobscured; verify with real pointer and Tab input, not only an element-level `.click()`.
- **A touch target inside a scaled canvas must also be CAPPED at the size of what it belongs to.** `calc(44px / var(--kf-zoom))` is correct for the floor and unbounded upward: at 0.4 zoom that is 110 layout pixels, which measured wider than the whole 32x17 card, so `elementFromPoint` at a card's centre returned the fold BUTTON and clicking a person opened a fold instead of their panel. A control may overhang its card's edge; it may never eclipse it.
- **A touch target inside the canvas must be sized in `1 / zoom`, because everything in `.react-flow__viewport` is in a scaled layer.** A `size-11` (44px) fold button measured 35px on screen at 0.785 zoom and would be 7px at the 0.15 floor. The fix is `calc(44px / var(--kf-zoom, 1))` with `--kf-zoom` published onto the viewport element by TreeCanvas, so the hit area is 44 SCREEN px at every zoom (verified live at 0.785, 0.654 and 0.545) while the visible pill stays 20x14. Two traps: a Tailwind arbitrary-value utility (`size-(--kf-hit)`) resolves the variable where it is DECLARED, so it read the `:root` fallback of 1 and still measured 35px -- the value has to be referenced inline on an element inside the viewport; and the offset must scale with it (`calc(-22px / var(--kf-zoom, 1))`) or the pill drifts off the card edge as you zoom.
- **A bottom sheet on a phone gets at most 55% of the CANVAS, not 70% of the screen.** At 375x812, 70dvh is 568px of sheet against 244px of canvas -- and the header, demo banner and search box already own most of that, so the card you just tapped was itself covered. A detail panel that hides its own subject has lost the thing that makes it a panel rather than a page, since this one is deliberately non-modal so a person can be read against the family around them. 55dvh alone still came to 447px against a 620px canvas region signed in and 563px in the demo, so 0.8.0 caps it at `min(55dvh, 55%)`: measured 310px of a 564px canvas, with the tapped card above it.
- **Collapse blocks the UNION, never the person, and that asymmetry is the data model showing through.** Parentage hangs off `unions`, so a mother's own outgoing edges are the PARTNER edges joining her to her partnerships -- block those and the couple comes apart, leaving a marriage rendered with one participant. Folding descendants therefore blocks the unions she partners in, which also means folding a mother's descendants folds the father's: they are the same children, and the union is the thing that says so. Upward is the opposite (a person's parent unions ARE their up-edge targets), so the block sits on the person. Found by a test that asserted both halves of the contradiction, before the suite was removed.
- **A collapse walk seeded from the ROOTS cannot fold ancestors, because the roots are what an upward fold hides.** The first implementation let every folded grandparent back in through the front door and an upward collapse silently did nothing. `entryPoints()` disqualifies anything behind a blockade and seeds from everybody else, so a fold stays LOCAL -- collapse one person in a tree of 216 and the other 215 are still entry points, where seeding from the collapsed node alone would leave a canvas holding one branch. The viewer and every collapsed node are anchors regardless, or folding your own ancestors empties the graph.
- **Disqualifying folded nodes as SEEDS is not enough: the walk must never ENTER them.** Until 0.8.0 a sibling, who is not behind a fold of their brother's ancestors, seeded the walk and climbed straight back up into the parents the fold hid -- 0 of 176 ancestor folds on the sample hid anybody -- and a married-in spouse brought back their partner's whole line below a descendants fold. `shadows()` in [lib/tree/collapse.ts](lib/tree/collapse.ts) computes what is behind every blockade, adds anybody whose every family link (childless partners included) leads behind it, and the walk refuses those nodes; an anchor behind a fold keeps only its own path back. Measured: 176/176 ancestor folds and 77/77 descendant folds hide somebody.
- **Folds and the visited trail live ABOVE the provider key.** `TreeCanvas` keys its `ReactFlowProvider` on detail level and arrangement, so `d` or orbit remounts the canvas; folds and the breadcrumbs held inside it were silently reset by every remount. They are held by the exported wrapper and handed down, as the viewed person is held by the stage.
- **A union dot is the MARRIAGE, not a route to the children, so it survives a fold that hides them.** It is dropped only once fewer than two of the nodes it joins remain -- which is the single-parent case, where the dot would otherwise hang below the parent pointing at nobody.
- **React Flow error#004 ("parent container needs a width and a height") is not always noise.** While the container measures 0x0 React Flow never measures nodes, so edges render as an empty container. Framing keys off `useNodesInitialized`, not `requestAnimationFrame`, for exactly this reason.
- **Only the INNER card animates on entrance, never the node wrapper.** React Flow owns the wrapper's `transform` for positioning; animating it fights the layout and the node lands in the wrong place. Hence `.kf-enter > *` in globals.css rather than `.kf-enter`.
- **Import `getNodesBounds` from `useReactFlow()`, not the package root.** The standalone export has no node lookup, cannot handle sub-flows, and warns on every single call.
- **The fusion reveal reads `contributingTreeIds.length`, so it is a property of the data, not a flag.** Mine-only mode produces `merged 0` and therefore no stacked sheets, automatically. The sheets carry no `z-index`: they and the card are all `z-index: auto`, so paint order alone puts the card on top, and that survives an ancestor gaining a stacking context in a way a negative index would not.
- **Feeding React Flow's own CSS variable beats overriding its selector.** Their `.react-flow__background-pattern.dots { fill: ... }` ties a `.react-flow .react-flow__background-pattern` override on specificity and then wins on source order, because their stylesheet is imported after globals.css. Setting `--xy-background-pattern-color` on `.react-flow` lands, since their rule reads it. This also means the `color` prop on `<Background>` must be REMOVED, not just left unset: it writes `--xy-background-pattern-color-props`, which they check first.
- **`.react-flow__background` renders OUTSIDE `.react-flow__viewport`.** The pane carries the pan transform and the background does not (confirmed on a live element), which is exactly what lets the edge-fade `mask-image` stay screen-fixed while the tree pans under it. Anything else placed in that SVG inherits the same non-panning behaviour.

## Repo-specific rules

- **A keyboard shortcut and its help row come from ONE array** (`BINDINGS` in [components/tree/TreeShortcuts.tsx](components/tree/TreeShortcuts.tsx)). A handler in one file and a documented list in another drift on the first change, and a help sheet that lies is worse than none. Single letters need the typing guard: without it, typing a name into search zooms, fits and cycles the detail level on the way through.
- **The card's pointer-tracked wash writes CSS custom properties, never React state.** Ported from `brand/portfolio-react`'s `GlassCard`, with three deliberate departures: its `useState` + rAF pair re-renders on every pointermove, which React Flow answers by re-measuring the node -- ruinous across the sample's 216 cards, so `--kf-mx`/`--kf-my` are set directly on the element; its 3D tilt is dropped, because React Flow owns the wrapper's `transform` for positioning; and its `useReducedMotion` gate is dropped, which that repo's own CLAUDE.md forbids in new code. The scheme-specific `--kf-wash-alpha` keeps the accent wash as texture rather than information.
